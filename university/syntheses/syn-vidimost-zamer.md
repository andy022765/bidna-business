# Synthesis: vidimost/zamer — как честно мерить видимость (Смотритель)

_Last updated: 2026-09-24. Основано на 16 источниках, 10 claims и seed-документах (RAZVEDKA-GITHUB, PLAN-SVOYA-VIDIMOST, VIDIMOST-SVOYA, лендинг /visibility/). Автор: geo-mekh._

## Current understanding

**Видимость — это распределение, а не место.** Независимые команды на разных рынках пришли к одному выводу. ИИ почти никогда не повторяет один и тот же список брендов: одинаковый список выпадает реже раза на 100 запусков, одинаковый порядок — примерно раз на 1000. Первое место меняется от запуска к запуску одинаково в браузере и в API (n-same-ai-list-rarely-repeats). Между соседними днями меняется около 65% процитированных источников. Повтор через две недели не отличается от повтора в тот же день, то есть это случайность генерации, а не дрейф (n-ai-sources-turn-over-65pct-daily, n-local-answer-churn-is-sampling-noise). При этом доля ответов, в которых назван бизнес, по многим запускам осмысленна и стабильна (n-mention-share-valid-metric). Отсюда c-0100: **метрика — доля ответов с упоминанием по каждому движку с интервалом; место в списке и скриншот одного ответа метрикой не являются.** Наши внутренние решения («место не показываем», «разброс, а не одно число», «видимость 17% одной цифрой — гороскоп») с этим совпадают.

**Сколько повторов.** Для доли упоминаний бренда стандартная ошибка опускается ниже 0,10 примерно к 7 запускам на вопрос (n-seven-runs-per-prompt-brand-rate). В режиме с веб-поиском список короткий (медиана 8 организаций) и закрывается к 10–15 запускам. Один запуск видит 62–77% набора из пяти. Без поиска новые имена продолжают появляться и на 15-м запуске (n-grounded-brand-lists-close-fast). Обзор 2026 года советует не фиксировать магическое число, а подбирать его по пилоту под нужную ширину интервала (n-geo-measurement-protocol-minimum). **Наши 3 прогона на движок ниже рекомендованного минимума** (c-0107). Поднять до 7 при нашей себестоимости стоит копейки: по расчёту RAZVEDKA, API на клиента — единицы долларов в месяц.

**Какие вопросы.** Живые формулировки одного намерения почти не похожи друг на друга: сходство 0,081. Но набор названных брендов определяется намерением, а не точной фразой (n-human-prompts-vary-intent-stable). Поэтому важнее верно выбрать 3–5 намерений покупателя и дать по 3–5 перефразов каждого, чем угадать «ту самую фразу». Вопросы должны быть нейтральными, без имени клиента: по имени модель узнаёт почти всех, а на общий вопрос называет единицы (n-recognition-not-recommendation). Считать вопросы с именем клиента в доле видимости нельзя; в RAZVEDKA это уже отмечено как ошибка чужого кода.

**Какие движки и в каком виде.** Движки почти не делят источники и поставщиков, поэтому считаем каждый движок отдельно (c-0105). Законно опрашивать можно ChatGPT, Claude и Perplexity через официальные API с поиском и городом. Gemini с поиском запрещён условиями Google. AI Overviews и AI Mode снимаются только сторонними сборщиками, это серая зона (seed: RAZVEDKA). Официальная и бесплатная замена для Google — отчёт Generative AI в Search Console клиента. Он показывает показы страниц сайта, а не упоминания в тексте (n-search-console-generative-ai-report, c-0110). API — «чистый аноним» с городом. Приложение учитывает IP и память пользователя. Прямого сравнения «API против приложения» на вопросах «ниша + город» мы не нашли. Żatuchin показал одинаковую нестабильность первого места в браузере и в API, но это не сравнение состава. Ответы без веб-поиска — это исход, а не брак: в одной конфигурации ChatGPT не искал в 57,8% запусков. Их надо сохранять и показывать отдельной строкой (n-no-search-answers-stay-in-denominator).

**Язык — отдельное измерение.** Язык вопроса решает, появятся ли «свои» поставщики. Замер только на английском занижает видимость местных и сообщественных брендов (c-0106). Для клиента, у которого часть покупателей русскоязычная, нужны два набора вопросов. Это расходится с нынешним замыслом «вопросы по-английски» (contr-010).

**Промежуточный показатель — роботы.** Документация трёх вендоров делит роботов на три роли: обучение (GPTBot, ClaudeBot), поисковый индекс (OAI-SearchBot, PerplexityBot, Claude-SearchBot) и заходы по вопросу пользователя (ChatGPT-User, Perplexity-User, Claude-User). **Сигнал «кто-то спросил, и движок пошёл к нам» дают только *-User** (c-0108). Наш счётчик относит SearchBot к «живому вопросу», и это завышает промежуточную видимость (contr-011). Google так не меряется вовсе: Google-Extended — не User-Agent, AIO и AI Mode отвечают из индекса Googlebot. Это уже зафиксировано в нашей рабочей заметке.

**Кейсы и контроль.** Сырые «рост в N раз» завышают эффект, потому что платформы растут сами. Честное сравнение требует контрольной группы (c-0109). Для замера клиента и нашего кейса 22.12 это значит: держать часть замороженных вопросов (или страниц) без работы как контроль. Смена модели, числа повторов или вопросов — разрыв базовой линии, его надо помечать (seed: RAZVEDKA, «отпечаток настроек»).

**Гарантия на лендинге.** Критерий возврата «назвали хотя бы в одном из 27–45 ответов» шумный в обе стороны (c-0115). При 3 повторах видна лишь часть устойчивого набора. Движки без поиска подкидывают редкие имена, так что одно случайное упоминание может закрыть гарантию без реальной видимости. А бизнес с истинной долей 5–10% за 27 ответов может не выпасть ни разу. Базовая вероятность нуля у малого бизнеса высока (c-0102). Юридический статус гарантии разобран отдельно (contr-002).

## Open questions

- **API против приложения.** Насколько состав названных бизнесов в API с поиском и городом совпадает с приложениями ChatGPT (с логином и без), Perplexity и AI Mode. Внутренний план (RAZVEDKA, «калибровочный замер API против приложений») этот вопрос уже ставит. Независимых данных по вопросам «ниша + город» нет.
- **Какой должна быть ширина интервала для решений.** Какую разницу между 0-м и 90-м днём считать реальной. Нужен пилот: бутстрэп по вопросам на нашем нулевом замере при 3, 7 и 10 повторах.
- **Язык.** Насколько на наших вопросах различаются наборы названных бизнесов на RU и EN (contr-010).
- **Сопоставление имён.** Какой процент упоминаний клиента теряется на вариантах имени и транслитерации: на Бали 38% «несовпадений» оказались вариантами. Для русских названий с английской транслитерацией риск выше. Нужен словарь вариантов имени клиента.
- **Условия Perplexity о хранении ответов** не прочитаны (seed: RAZVEDKA). Их нужно прочитать до продажи замера.

## Contradictions

- [contr-010] — вопросы для замера задуманы только на английском, а язык вопроса меняет, кого называют.
- [contr-011] — счётчик роботов относит SearchBot к «живому вопросу», а документация — к индексации.
- [contr-002] (не наш, связан) — гарантия возврата против оферты. Качество самого критерия — c-0115.

## Strategy implications

Что это значит для Смотрителя и для того, как мы продаём замер:

1. **Протокол Смотрителя v2** (предложение, решает Андрей):
   - 3–5 намерений покупателя × 3–5 перефразов каждого, без имени клиента;
   - по 7 повторов на вопрос и движок, разнесённых по 2–3 дням окна замера;
   - ChatGPT, Claude и Perplexity через API с поиском и городом в параметре; Google — через отчёт Search Console клиента, если есть доступ;
   - RU и EN отдельно для клиентов с двуязычными покупателями;
   - ответы без поиска сохраняются и показываются отдельной строкой;
   - словарь вариантов имени клиента (транслитерация, LLC/Inc, прежние названия);
   - итог — доля ответов с упоминанием по каждому движку и языку с интервалом, посчитанным по вопросам;
   - 1–2 контрольных вопроса без работы;
   - отпечаток настроек (модель, дата, число повторов); его смена помечается как разрыв базовой линии.
2. **Что говорить клиенту о замере:** «меряем, что нейросеть отвечает на анонимный вопрос из вашего города, по каждой нейросети отдельно, много раз, потому что ответы случайны; показываем долю и разброс, а не место». Это честно и отличает нас от трекеров с «видимостью 17%» (c-0100).
3. **Промежуточный показатель для клиента** — в три шага: «прочитали для обучения» → «проиндексировали для поиска» → «пришли по вопросу человека». Событие для отчёта — первый заход *-User. Правка счётчика — в полосе ГОЛОС (contr-011).
4. **Гарантия.** Андрею стоит решить, оставить ли критерий «хотя бы одно упоминание из 27–45» или заменить его на устойчивый. Например: «назвали хотя бы в двух прогонах одного движка» или «доля выросла сверх разброса нулевой точки». В любом случае считать только ответы с поиском и записать движки и число повторов в условия (c-0115, contr-002).
5. **Не мерить чаще раза в квартал для отчёта «было / стало».** Промежуточные прогоны допустимы для внутренней диагностики, но клиенту как тренд не показываются (c-0114).
6. **Смотритель — инструмент, а не отличие.** Готовые трекеры дешевле и замер отдают бесплатно (seed: RAZVEDKA; лендинг). Наше отличие — честный протокол и работа между замерами. В продаже это и подчёркиваем.
